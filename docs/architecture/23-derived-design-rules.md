## 23. Derived design rules

1. **Assume the agent can be corrupted. Security must still hold.** [Z-RULE-1]
2. **Treat agents as developers/operators and enforce normal DevOps, GitOps, cloud-native, and zero-trust principles.** [Z-RULE-2]
3. **Do not reinvent controls that OpenShell, GitLab, Kubernetes, Cilium, Kyverno, Tetragon, SPIFFE, OpenBao, CI/CD, or GitOps already provide well.** [Z-RULE-3]
4. **The capability is the operation, not the CLI executable.** [Z-RULE-4]
5. **Agents receive capabilities, not ambient credentials.** [Z-RULE-5]
6. **Authorization happens before privileged authentication is delivered.** [Z-RULE-6]
7. **Runtime controls apply to child processes and build code, not just the agent binary.** [Z-RULE-7]
8. **No normal Docker socket inside an agent environment.** [Z-RULE-8]
9. **Normal agents may write DEV/QA and feature branches; production mutation is out of scope for v1 and production diagnostics are one-shot, filtered, and read-only.** [Z-RULE-9]
10. **Agents may investigate production only through Phantom Proxy-mediated diagnostics; humans and controlled delivery systems change production.** [Z-RULE-10]
11. **Protected branch, CI, code review, GitOps, RBAC, admission, and network/runtime policy remain security boundaries.** [Z-RULE-11]
12. **Tool output, repository content, logs and external data are untrusted input.** [Z-RULE-12]
13. **Network egress is a security control, not merely connectivity configuration.** [Z-RULE-13]
14. **Real credentials should be bound to destination and operation where possible.** [Z-RULE-14]
15. **The agent must not be able to disable its own security controls.** [Z-RULE-15]
16. **Visibility is not authorization.** [Z-RULE-16]
17. **Plugins/extensions provide UX and context, not the hard security boundary.** [Z-RULE-17]
18. **Audit and remote revocation are mandatory parts of the security model.** [Z-RULE-18]
19. **Neither developers nor agent sandboxes receive real secrets; real secret material remains behind the Phantom Proxy.** [Z-RULE-19]
20. **Authenticated remote access traverses the Phantom Proxy; public unauthenticated access may go direct only under egress policy.** [Z-RULE-20]
21. **Optional AI scanners are defense-in-depth only and may make handling stricter, never weaker.** [Z-RULE-21]
22. **Contextual risk models may only escalate deterministic risk.** [Z-RULE-22]
23. **Dependency/package access is a distinct capability class; enterprise defaults should prefer approved internal mirrors/proxies.** [Z-RULE-23]
24. **Arbitrary code execution is allowed inside the default OpenShell sandbox; the sandbox boundary, not command allowlists, is the primary containment mechanism.** [Z-RULE-24]
25. **Strict command allowlisting may be offered as an optional hardened mode.** [Z-RULE-25]
26. **Every agent-created commit is signed by the active security-epoch SPIFFE identity; unsigned agent commits are forbidden.** [Z-RULE-26]
27. **Repository instructions and MCP/tool output are untrusted context and never grant authority.** [Z-RULE-27]
28. **Use specialized/native enforcement where it already exists; Z3R0 fills agent-specific gaps rather than replacing mature DevOps/GitOps/cloud-native controls.** [Z-RULE-28]
29. **Phantom Proxy is HTTP(S)-first and is implemented primarily through OpenShell provider substitution, supervisor mediation, and Z3R0 middleware rather than a separate host-wide TLS MITM.** [Z-RULE-29]
30. **OpenShell is the primary Z3R0 runtime substrate; Z3R0 should not build a competing sandbox/runtime unless a proven gap requires it.** [Z-RULE-30]
31. **OpenShell low-level policy and formal policy checks complement, but do not replace, Z3R0 semantic capabilities and human-accountable approval.** [Z-RULE-31]
