# Caveats

Format: `CNN — <area> — <issue>` + impact/mitigation.

- C01 — OpenShell — All capabilities in arch doc Appendix A are assumptions, not verified. Must be proven in Sprint 01.
- C02 — Platform — Landlock/seccomp are Linux-only; macOS/Windows gaps unknown.
- C03 — OpenShell — Workspace is uploaded (copy), not bind-mounted; edits need sync back to host repo or git push from sandbox.
- C04 — OpenShell — Telemetry on by default; set `OPENSHELL_TELEMETRY_ENABLED=false`.
- C05 — Host — Podman 6.1.3 is manual install in /usr/local/bin: outside OpenShell's documented 5.x, no package signature/updates. Verify origin, update manually.
- C06 — Host — Podman user socket = full user authority. Agent must never reach it (proved in F02).
- C07 — Host — AppArmor userns exception for /usr/local/bin/podman (mirrors Ubuntu's podman profile).
- C08 — Host — Image policy allowlists registries but does not verify signatures. Add sigstore/GPG verification later.
- C09 — OpenShell — `sandbox exec` uses login shell; image `ENV PATH` is lost (golang image: pass `--env PATH=/usr/local/go/bin:...`). Fix via custom image/profile.
- C10 — OpenShell — `sandbox upload <dir> <dest>` creates `<dest>/<basename>`; respects .gitignore. Copy, not sync (confirms C03).
- C11 — OpenShell — `/proc/mounts` in sandbox leaks host paths (`/home/<user>/.local/share/containers/...`) → username leak. Low risk; no content access.
- C12 — Image — setuid binaries (`su`, `passwd`) present in golang image; neutralised by NoNewPrivs=1 + empty CapBnd + Seccomp=2. Prefer minimal images.
- C13 — OpenShell — Gateway runs as the login user; provider secrets in `~/.local/state/openshell/gateway/openshell.db` are encrypted, but `credentials/key-encryption-key.bin` is next to it, same owner. Breakout → all secrets. Fix: F09.
- C14 — OpenShell — `sandbox delete` is async; re-creating the same name immediately can fail (harness printed 0 results once). Wait or use unique names.
- C15 — OpenShell — Credential rewrite only for HTTP the proxy inspects; `tls: skip`/non-HTTP endpoints get no rewrite (and no L7 check).
- C16: sandbox DNS is synthetic (198.18.0.0/15); tools that validate resolved IPs or need real DNS (SRV, TXT) may break.
- C17 (medium): placeholder laundering. Proxy resolves the placeholder in query, ANY header (not only the bound one) and basic auth on the bound endpoint (F08: launder:*); body and path not. If the bound API echoes or stores that input (echo service, issue title via query, custom header logged), the real secret comes back to the agent. Proxy does not redact secrets in responses. Do not bind creds to debug/echo endpoints.
- C18 (high): foreign-key exfil. Agent sends its own/attacker key (Authorization, X-Api-Key, ?api_key) to an allowed endpoint → data lands in attacker account. Proven by PoC03 foreign-* FAIL. OpenShell rules match method/path/query only, no header matchers. Mitigation: query allowlist; headers need upstream feature or our own egress/LLM gateway that strips+injects auth.
- C19 (inherent): every allowed endpoint is an exfil channel (data in query/path/body). Only mitigation: few endpoints, read-only, tight path/query rules, Z3R0 audit.
- C20 (high): `sandbox download` of a git repo copies `.git/config` + hooks. `git status` on host then runs agent code (core.fsmonitor proven, F08 dl:git-fsmonitor-host-exec). Rule: never download repos to host; agent output reaches host only via git push → GitLab MR review (fetch, don't copy .git). Note: `.git/config`/hooks are not versioned, so push/fetch/clone do not carry this vector; it exists only when a raw `.git` dir is copied (download, rsync). Committed content (.gitattributes, .vscode/, .envrc, Makefile, pre-commit, go generate) is a separate risk (catalog A10/X01): treat as untrusted, run only in sandbox/CI.
- C21 (medium): `sandbox download` keeps absolute symlinks to host paths (e.g. ~/.ssh). Later tools on host may follow them. Write-through on re-download and relative traversal are blocked.
- C22 (medium): no disk quota; sandbox writes to host disk (overlay + workspace volume). Agent can fill host disk. Mitigation: dedicated partition/XFS project quota for podman storage of the gateway user (F09).
- C23 (low): memory exhaustion OOM-kills the sandbox (exit 137, phase Error, no restart). Host safe (4 GiB cgroup), but work in sandbox is lost. Push work early.
- C24 (inherent, containers): shared host kernel, version visible → exploit hints. Mitigation: patch kernel; VM driver (F09/C13).
- C25 (high): login user `bree` is in group `docker` (rootful Docker 29.5.2) → any breakout as bree = host root. Mitigation: gateway as dedicated user not in docker group (F09); consider removing bree from docker group.
- C26 (medium): login user holds the gateway mTLS client key. Breakout as login user = full gateway API: create sandboxes with any provider attached → use (not read) stored credentials via proxy, change policies. Mitigation: short-lived client certs / OIDC, per-user provider scoping (later).
- C27 (high, extends C17): real agent proven (PoC04 attack.sh): injected AGENTS.md makes agent curl bound endpoint with `?t=$ECHO_TOKEN`; proxy resolves, echo returns real secret → secret in agent context, session store and sent to the LLM provider. Mitigation: never bind creds to reflecting endpoints; query deny rules (F10); own egress proxy.
- C28 (medium): Copilot via Remote-SSH: GitHub/Copilot auth token is used by the VS Code server inside the sandbox (in process memory, not proven on disk). Breakout from `node` = Copilot token. Copilot endpoints allowed only for `/sandbox/.vscode-server/**`; but any code the agent writes there could run as that binary path. Mitigation: VS Code server dir read-only after install (later), short-lived token.
- C29 (low): default policy blocks `/dev/pts` → VS Code/Copilot terminal `forkpty` fails. Needs `--policy` at create with `/dev/pts`,`/dev/ptmx` read_write (filesystem policy is startup-only). Host wildcard `*.x.com` matches one label only (`api.enterprise.githubcopilot.com` needs own entry).
- C30 (medium): `zero` has no sync-back. Work inside the sandbox exists only there; `zero rm` deletes it. Only exit path per C20 is git push from the sandbox → F12.
- C31 (low): `zero code` (VS Code Remote-SSH via zero) and `zero rm` not exercised after the Go rewrite; `zero run` reached the model API but OpenCode Zen free tier rejects non-TUI `run` ("can only be used from within OpenCode").
- C32 (high, upstream): E3 VM sandboxes unusable on openshell 0.1.2 and 0.1.4 — guest dies at capability probe `read /proc/self/status: Permission denied` (NVIDIA/OpenShell#4014, all images, policy on/off). F16 blocked until fixed. No `openshell sandbox logs` CLI either; console only via sudo into driver state dir (upstream UX gap, noted on the issue).
- C33 (medium, upstream): openshell 0.1.4 podman driver no longer provides the /sandbox mount (sandbox HOME=/go). Any tooling assuming /sandbox breaks. zero moved its workspace to /tmp/zero (policy read_write /tmp).
- C35 — 2026-11-10 — zero GitLab token (D20): profile `zero-gitlab` allows git/curl to all of gitlab.com read-write; the token's project scope is the real limit. Existing profile is never updated by zero (`openshell profile update` needs resource_version); after editing `internal/zero/gitlab-profile.yaml` run `openshell profile delete zero-gitlab`. Token is only minted on sandbox create; a sandbox older than 1 day has an expired token → `zero rm && zero up`. Dev image has no glab; API use is curl with `Authorization: Bearer $GITLAB_TOKEN`.
- C36 — 2026-11-10 — (high, upstream) OpenShell 0.1.4 closes the connection (curl exit 56, glab `EOF`) on any `%2F` request-target to an enforce REST endpoint. glab encodes the project path (`projects/group%2Fsub%2Frepo`) in almost every command → `glab mr list`, `glab ci list` fail in the sandbox; `glab api projects/<id>` works. Endpoint option `allow_encoded_slash: true` fixes it (tested) but relaxes path matching → NOT applied, applied per D22. Upstream: NVIDIA/OpenShell#4671 (no 403 on encoded slash). Report: `upstream/openshell-encoded-slash-glab.md`.
- C37 — 2026-11-10 — (medium, upstream) `/usr/local/bin/opencode` in the dev image is a uniget symlink. Provider profile binaries are stored by resolved path, but `openshell policy update --binary /usr/local/bin/opencode` stores the literal symlink path, which never matches the running `opencode.exe` → opencode got `ECONNREFUSED` to opencode.ai / models.opencode.ai (MCP via the profile worked). zero now passes the real executable path (`opencodeBin` in commands.go); breaks if the image layout changes. No warning from `policy update`. Related: NVIDIA/OpenShell#4834, #2883. Report: `upstream/openshell-policy-update-symlink.md`.
- C38 — 2026-11-10 — (high, upstream) opencode 2.x removed `attach URL -p --dir` / `run --attach`; new form is `--server URL` + `OPENCODE_SERVER_PASSWORD`. With `--server` the client sends its own cwd (or resolves the positional dir locally) → `Location not found: /tmp/opencode/developer`. `zero attach` and `zero run` are broken until fixed. Upstream: anomalyco/opencode#47665 (fix PR #47818 closed by bot). Not worked around (no mirrored host paths in the sandbox). Report: `upstream/opencode-server-remote-directory.md`.
- C39 — 2026-11-10 — (low, upstream) `opencode mcp list` prints "No MCP servers configured" although `opencode debug config` shows `mcp.servers.gitlab`. Upstream: anomalyco/opencode#63053.
- C40 — 2026-11-10 — (medium, zero) the ssh forward started by `zero up` dies when the calling shell exits (child of the caller, not detached). `zero status` then shows `forward: off`. Fixed: forward runs in its own session (setsid).
- C41 — 2026-11-10 — (medium, zero, TODO) `zero install` downloads OpenShell 0.1.4 release tarballs from GitHub. Upstream publishes only sha256 checksum files, no signatures/attestations → zero pins the sha256 in `internal/zero/install.sh` (protects against later tampering, not a tampered release at pin time). TODO: decide on verification (upstream signing request, distro package, or own mirror).
- C42 — 2026-11-10 — (high, zero) agent-written code executes on the host when the developer checks out an agent branch and runs tooling: committed hook configs (`.pre-commit-config.yaml`, `.husky/`, `lefthook.yml`), `.envrc` (direnv), `.vscode/tasks.json`/`settings.json`, `Makefile`, `go:generate`, test files. `.git/hooks`/`.git/config` do not travel (F12). Runs as the login user → full host blast radius. Not enforceable by OpenShell (sandbox boundary ends at push). Mitigation: review MR diff before running anything from an agent branch on the host; prefer working on agent branches inside the sandbox (`zero web`/`zero code`); CI runs untrusted code in its own isolation. Open: `zero doctor`/`zero review` could flag changes to these paths.
- C43 — 2026-11-10 — (high, GitLab, TODO) the agent can push to, overwrite or delete any branch its token's role allows, not only its own session branch. GitLab fine-grained tokens limit by group/project/user/instance, never by branch; OpenShell 0.1.4 L7 rules see only method/path/query, and `git-receive-pack` carries branch names in the body. Only protected branches are safe. Owner: GitLab (ADR 0024). Later options: GitLab feature request for branch-scoped tokens; zero publishes only the session branch from the host (token without `push_code`); OpenShell git-aware receive-pack rules. See attack path P25.
- C44 — 2026-11-10 — (medium, zero/OpenShell 0.1.4) credential rotation via `openshell provider update` works for new processes only. Tested: new ssh session gets a new placeholder version (`v1279…` vs `v1305…`) resolving to the new token (200); the old placeholder stays pinned to the old secret → after revoking the old token it returns 401. Long-running processes (`opencode serve`, its GitLab MCP) keep the old placeholder and break on rotation. Token renewal must therefore restart serve (or rotate only on `zero up`). Likely intended (versioned placeholders), not filed upstream. Deferred: revisit with OpenBao as credential broker (arch §8, Z-P0-5).
- C45 — 2026-11-11 — (high for P1, uniget) Quadlet unusable on this host: uniget `podman` 6.1.3 ships `/usr/local/libexec/podman/quadlet` dynamically linked against musl (`/lib/ld-musl-x86_64.so.1`), Ubuntu 26.04 has no musl loader → systemd user generator fails silently, `openshell-gateway-ctr.service not found`. Report: `ai-docs/upstream/uniget-podman-quadlet-musl.md`. Blocks P1 (Quadlet).
- C46 — 2026-11-11 — (medium, OpenShell 0.1.8 + glab 1.128.0) since OpenShell 0.1.8 the supervisor substitutes a credential only in its declared placement (`zero-gitlab`: `Authorization`). glab sends PATs as `PRIVATE-TOKEN` → `403 credential_placement_mismatch` for every `glab` API call; git, curl Bearer and GitLab MCP unaffected. Switching the profile to `PRIVATE-TOKEN` breaks git, curl and MCP (tested). Applied (ADR 0026): sandbox env `GLAB_IS_OAUTH2=true` → glab sends `Authorization: Bearer`, which GitLab accepts for PATs. Risk: relies on glab treating the token as OAuth (non-user-settable key, env only). Upstream: `ai-docs/upstream/openshell-multi-placement-credential.md`.
- C47 — (accepted, ADR 0028) 2026-11-11 — (medium, containers/image, podman 6.2.0) podman `policy.json` `sigstoreSigned.fulcio` requires `subjectEmail`; GitHub Actions keyless certs carry only a URI SAN (workflow identity). So the CI-signed dev image (`ghcr.io/breee/z3r0-dev`, cosign verify OK) cannot be verified by podman policy. Report: `ai-docs/upstream/containers-fulcio-uri-san.md`. (#69)
